## 0. Verdict

Temper's foundation still holds: migrations match the committed schemas exactly, the restore choke point and envelope are sound, one-live-activity enforcement is transactional, the domain lane is deterministic and heavily tested, and the token layer has zero raw colour or size escapes. The 29–30 August rounds closed the P0 class. What this round finds is different in kind: **six of the eight P1 rows are in code that the last rounds wrote or reshaped** (the finished-work fingerprint gate, the occurrence generator, ADAPT_WEEK, the reminder receiver rewrite, the alarm-path completion, and the Home-start redesign that left the start sheet unhosted), and the two biggest performance regressions defeat two rows the ledger marks "done". The product rule that matters most on the floor — every progression step is a loadable plate — is broken for pound users by a rounding path that a code comment claims to have fixed.

Nothing here requires a schema change to fix except the two time-zone rows, which are explicitly flagged as v5 candidates.

One tooling defect surfaced while doing this: `tools/preflight.sh` deletes any hand-assembled jar directory whose `annotations-*.jar` path does not contain `org.jetbrains/annotations` (lines 89–105), and its bootstrap cannot resolve JUnit from a Gradle distribution's `lib/` because it demands a `junit/junit/` path fragment (line 71). On a machine with no Gradle module cache the JVM lane is unreachable through preflight even when every jar is present. Fix: test jar *contents* (`unzip -l | grep NotNull.class`), not paths.

## 2. Ranked defects

Severity: **P0** data loss or crash · **P1** primary journey broken, or completed data silently mutated · **P2** recurring friction, contract breach, or measurable perf regression · **P3** polish. Confidence: verified-by-reading unless marked *likely* or *needs device check*.

### P1

**D1 ✔ Pound users' progression drifts off the 5 lb grid.** `domain/ProgressionCalculator.kt:53` adds `STEP_LBS_IN_KG` (2.26796 kg) to a kilogram value already on the 0.1 kg grid and re-quantises to 0.1 kg, so every step lands 2.3 kg = 5.07 lb up; `WeightConverter.toDisplayValue` then rounds to the half pound. Simulated from 100 lb, hit target every session: 105 → 110 → **115.5** → 120.5 → 125.5 → … → **151** at step 10. The strip, the coach card, the prefilled well, `PlateMath` ("…and 0.5 leftover") and history all show it; a typed "115" stores 52.2 kg while the accepted suggestion stores 52.3 kg, which re-opens the reps-at-weight record split the ledger's `2d7a6d2` closed. The comment above line 53 claims the quantisation prevents exactly this. Kilogram users are unaffected. **Fix:** step in display units the way `WeightConverter.incrementKg` (`WeightFormat.kt:70-73`) already does — `toKg(toDisplayValue(lastKg, unit) + sign × displayStep, unit)` — and add a 12-session walk test in both units asserting `toDisplayValue == 100 + 5n`. `ProgressionCalculatorTest.kt:49-73` only checks one step with a 0.05–0.1 tolerance.

**D2 ✔ On the alarm path the rest service is never told to stop; a stale negative countdown stays on the lock screen.** `timer/RestTimerCompletion.kt:58-67` stops the store with `stopIfCurrent(id, fromService = true)`, and `RestTimerController.stop` (`:100-111`) skips `ACTION_STOP` when `fromService`. The follow-up `NotificationManager.cancel(RUNNING_ID)` is a no-op on a foreground-service notification (its own comment says the service teardown removes it). That teardown is `handler.postDelayed(completeRunnable, delayMs)` (`RestTimerService.kt:103-104`), an uptime-clock timer that does not advance while the CPU sleeps. Screen off, the `ELAPSED_REALTIME_WAKEUP` alarm fires on time, the cue plays, and the ongoing card stays with a chronometer counting "−0:42" and live ±15 s/Skip for roughly the rest's length; tapping it opens `RestLockActivity`, which `finish()`es. **Fix:** in `RestTimerService.onCreate` collect `controller.snapshot` and `stopNow()` when `!running`; drop the ineffective cancel. This also covers D-timer-5 (stopSelf without startId tearing down a +15 s extension). *Needs device check for the observed duration.*

**D3 ✔ Rules mint occurrences for days already gone and hours already passed.** `domain/OccurrenceGenerator.generateWeek` (`:36-73`) has no `today`/`now` input: every enabled rule lands on `weekStart.nextOrSame(rule.weekday)`. `ensureWeek` (`PlannerRepository.kt:232-253`) passes none; onboarding and the custom-week wizard call `publishPinnedWeek` immediately after setup; `DayBlocks.addCardio` defaults to 07:00 and `nextLaterHour` ignores the clock. Onboarding on Thursday 18:30 with Mon/Wed/Fri mints Monday and Wednesday at 18:00 → both overdue → Home opens with "2 planned sessions were not done", red cells, "3 planned · 0 done", two Still-open leftovers that were never scheduled, and the week's single missed-work decision burned before the first workout. A same-day cardio or Extra add is overdue at birth. Only `MissedWorkPolicy` ADAPT (`:94-98`) guards this, and its comment names the rule. **Fix:** give `generateWeek` `todayEpochDay` + `nowMinutes` and skip `(rule, date)` behind now for rules whose `createdAtMs` is after that date's start (old rules must still mint history at rollover); clamp same-day hours to `max(default, now + 1 h)` in `DayBlocks`, `AuxiliaryBlocks`, `PlanViewModel.addCardio`; give `ExistingLayoutMatcher.match` a `todayEpochDay`.

**D4 ✔ "Rebuild the rest of the week" deletes every Home "just today" block and every relocated session.** `MissedWorkPolicy.kt:81-105`: ADAPT treats every PLANNED row ≥ today as regenerable, regenerates from *enabled* rules on *their own weekday*, and returns everything not regenerated as `removed`; `PlannerRepository.applyMissedWork` (`:283-285`) deletes them. A once-row belongs to a rule that `DayBlocks`/`AuxiliaryBlocks` disabled after minting (`DayBlocks.kt:108,178`, `AuxiliaryBlocks.kt:65`); a "Do it today" or Move-remaining row sits on a day that is not its rule's weekday. Neither regenerates, so both are deleted while the vacated origin stays MOVED — the session vanishes from strip, Still open and summary. `MissedWorkPolicyTest` never exercises a disabled rule or a relocated id. **Fix:** treat as regenerable only rows whose `id == occurrenceId(ruleId, day)` *and* whose rule is enabled; keep everything else.

**D5 ✔ A stale reminder notification can rewrite a completed session.** `PlannerRepository.cancelReminders` (`:541-553`) and `WorkManagerReminderScheduler.cancelForOccurrence` (`:34-36`) cancel WorkManager jobs only; the posted notification is dismissed solely by `MainActivity` on a Start launch and by `ReminderActionApply`. A session started from Home (launcher → row → confirm → finish) leaves the 18:00 notification in the shade with live Snooze/Move/Skip. `skipOccurrence` (`:310-316`) and `moveOccurrenceForward` (`:400-434`) have no status guard, so Skip flips the DONE row to SKIPPED and Move marks it MOVED and mints a duplicate PLANNED row for the next day (orphaning `completedActivityId`). `ActivityRepository.confirm`/`completeLive` set DONE without touching reminders at all. **Fix:** guard Skip to `PLANNED|MISSED` and Move to `PLANNED`; make `cancelForOccurrence` also call `ReminderNotifications.cancel`; route the two `ActivityRepository` DONE writes through `PlannerRepository.markOccurrenceDone`.

**D6 ✔ Editing a finished set leaves History, Home and the heat/volume insights stale — a regression from the 30 August write-amplification fix.** `WorkoutDao.observeFinishedWorkGeneration` (`:52-71`) fingerprints finished work as session count, duration sum, last finish, working-set count and last set time. `observeSessionSummaries` and `observeFinishedSince` (`WorkoutRepository.kt:117-142`) re-run only when that fingerprint changes. `updateSet` (`:489-518`) changes weight/reps/RPE and none of those columns. After correcting a mistyped 100 → 60 kg in Session detail, that screen shows 60 while the History row, Home's "Last session" tile and every 32-day consumer keep the old volume until some other finished session is created or deleted. This breaks `UX_PAGE_PASS` page 9's gate ("Edit a finished set → heat and volume move"). **Fix:** add `COALESCE(SUM(sl.weightKg * sl.reps),0)` and `SUM(sl.reps)` (and RPE if any windowed consumer reads it) to the fingerprint and the matching fields on `FinishedWorkGeneration`.

**D6b ✔ The start sheet has no host, so unplanned cardio and backdated logging are unreachable.** `StartOptionsSheet` (`ui/workout/StartOptionsSheet.kt`) has zero call sites in `app/src/main`; the only remaining references are two comments. `log/{mode}` is reached solely from `HomeViewModel` with `"mixed"` for a planned MIXED occurrence (`:313`), and `cardio/{id}` only from a planned cardio row. "Log a past workout", an unplanned live run, and the sheet's "Go to session" are dead code — contradicting ADR-006 T2 ("Record a cardio activity, live or manual → Home or start sheet") and ADR-021 §2, and leaving `StartOptionsViewModel` (391 lines) and its tests maintained for nothing. Its cardio-discard branch (`StartOptionsViewModel.kt:290-294`) is also unguarded — the crash class the ledger fixed on the bar. **Fix (product decision):** either host the sheet on Body/History/Plan as `UX_PAGE_PASS` §4 still says, or delete it and add "Log a past activity / Start cardio" to Home's Add picker; guard the discard branch before re-hosting.

**D6c ✔ A reminder's Start tap is consumed only while Home is composed; its body tap starts a session with no confirm.** `openOccurrenceId` is handed only to the `Route.Home` composable (`AppNav.kt:408-409`) and consumed by `HomeScreen`'s `LaunchedEffect` (`:105-109`) with a direct `viewModel.startOccurrence(id)`. With the app warm on Plan, History, Settings or any pushed route, `MainActivity.onNewIntent` (`:68-88`) cancels the notification and marks the delivery STARTED, and nothing happens; the id waits until the user next opens Home, where the workout then starts — without the ADR-018 confirm — possibly hours later. Separately, the notification's *content* intent (`ReminderNotifications.openApp`, `:119-129`) carries the same `EXTRA_OCCURRENCE_ID` as the Start action, so tapping the body to look at today's plan starts the workout (and never marks the delivery STARTED). **Fix:** at nav level, `LaunchedEffect(openOccurrenceId) { goToTab(Home) }` before Home consumes it; give the content intent a distinct extra that selects the day and opens the confirm.

### P2 — product and data

**D7 ✔ Dead process + late alarm = silent rest.** `RestTimerRehydrator` classifies a same-boot expiry more than `LATE_ALERT_GRACE_MS = 60 s` old as `None` and the controller clears disk (`RestTimerStatePersistence.kt:126,173-179`; `RestTimerController.kt:156-159`); `rehydrate()` runs in `Application.onCreate` before the receiver, which then finds nothing (`RestTimerAlarmReceiver.kt:63-72`). Inexact alarms batch up to 75 % of futurity, and Android 14+ denies `SCHEDULE_EXACT_ALARM` by default for target 33+, so every fresh install is on that path. **Fix:** `Expired(late = true)` for any same-boot expiry; cue within grace, silent "Rest done" beyond.

**D8 ✔ The rest cue routes on the media stream.** `RestTimerAlerts.kt:63-64` calls `MediaPlayer.create(context, raw)` (which prepares) and only then `setAudioAttributes`, which the platform documents as ineffective after `prepare()`. Paused earbuds or media volume at zero silence the cue while `ringerIsSilent` models the notification stream. **Fix:** the four-argument `create(context, res, CUE_ATTRIBUTES, AUDIO_SESSION_ID_GENERATE)`. Related product decision (D-timer-4): `USAGE_NOTIFICATION` for tone and vibration means DND "priority only"/"alarms only" and vibrate mode silence rest entirely; clock apps use `USAGE_ALARM`.

**D9 ✔ The coach says "Back has no logged work" for a muscle trained 33+ days ago.** `TrainingInsights.kt:138-145` builds `coachBasis` from the 32-day windowed graph and never overlays lifetime recency (the display snapshot does, `:118-126`), so `daysSinceLastTrained` is null past the window and `RecommendationEngine.kt:235-247` renders a HIGH "no logged work" card beside a Body map that says "35 days since". `CoachBasisTest` passes an unwindowed list. **Fix:** overlay `MuscleRecency.byMuscle(lastLoggedAtByExerciseId, catalog)` into the basis; test through `TrainingInsightsCalculator`.

**D10 ✔ Double-tapping Log writes two sets.** `ActiveWorkoutViewModel.logSet` (`:769-865`) validates synchronously then launches with no in-flight flag; `PrimaryGymButton` has no debounce. Two identical sets, a second rest start, a possible double PR banner. **Fix:** a `logging` flag checked-and-set before the launch, `enabled = !logging` on `LogBar`. Same class: `applySuggestedWeight()` (`:975-978`) is the one draft mutation that does not `persistDraft()` ✔.

**D11 ✔ Three record/deload rules misread assisted and pre-block history.** `BlockReview.countRecords` (`:131-152`) seeds priors from in-block sets only despite its KDoc, so a 110×5 under a standing 150×5 counts as two records and a genuine opener never can. `DeloadSignal.kt:113` computes e1RM without `LoadClass`, so an assisted lift that *improved* (less assist) reads as regression and the lighter-week card fires on a progressing lifter. `PersonalRecords.kt:206-208` awards "Most reps ever" to an assisted set that added assistance. Fixes are local: seed `seen` from pre-block sets; resolve load class (assisted → negate); compare reps only at equal-or-less assistance.

**D12 ✔ Deleting or unpinning a rule cascades its DONE/SKIPPED/MISSED history.** `schedule_occurrences.ruleId → ON DELETE CASCADE` (`PlannerEntities.kt:29-38`); `removeTimedRule` (`PlannerRepository.kt:213-230`) documents "DONE rows stay as history", deletes PLANNED rows by hand, then `deleteRule` cascades the rest; `syncSlotsToRules` (`:85-91`) does the same on unpin. Yesterday's done credit disappears from the board, "0 done this week", and `ActivitySession.occurrenceId` dangles. The session itself survives in History, which is why this is P2 not P1. **Fix:** retire (`enabled = false`) any rule with non-PLANNED rows instead of deleting it; delete only PLANNED rows.

**D13 Zero-grace "overdue" plus Keep makes tonight's session unstartable at 18:01.** `MissedWorkPolicy.kt:19-20` counts a today row overdue one minute past its hour; Keep marks it MISSED (`:50-54`); `DailyAgendaCard.canOpenStart` (`:339-344`) starts MISSED rows only when they are leftovers from an earlier day. Move at 18:01 relocates tonight's session to tomorrow. **Fix:** day-based or ≥ 2 h grace for today's rows; allow a MISSED-today row to start (it resolves to `AlreadyThere`).

**D14 ✔ "Today" is captured once and never refreshed on three tabs.** `PlanScreen.kt:270` `remember { todayEpochDay() }`, `HistoryScreen.kt:99` `remember { LocalDate.now() }`, `HomeScreen.kt:173` unmemoised but with no resume or midnight trigger; `HomeViewModel` computes today inside its combine and only on upstream emission. A process kept alive overnight shows yesterday marked as today; Plan's Add session Volt opens yesterday as a past day and suppresses the picker (`PlanDayScreen.kt:72-80`). *Likely; needs device check.* **Fix:** one `TodayTicker` (re-read on `ON_RESUME` and at local midnight) exposed as a composition local / VM input; every `todayEpochDay()` in composition reads it.

**D15 ✔ Non-transactional and check-then-act planner/workout writes.** `moveOccurrenceForward`/`moveOccurrenceToDay` (`PlannerRepository.kt:400-464`) upsert the vacated row, call WorkManager, then upsert the replacement — reachable from the reminder Move receiver; a failure between the writes leaves a MOVED row with no successor and nothing regenerates it. `discardSession` (`WorkoutRepository.kt:705-709`) reads `finishedAt` then deletes; a live-bar Finish racing a stale-screen Discard can still delete a finished session (`ActivityRepository.discard` does the check inside the transaction). `addExerciseToSession`, `RoutineRepository.addExercise/moveExercise`, `ExerciseRepository.createCustom/updateCustom` are the same shape. **Fix:** `withTransaction` around each; `DELETE … WHERE id = :id AND finishedAt IS NULL` for discard.

**D16 ✔ Deleting a routine leaves `schedule_rules.routineId` dangling.** No FK on the column; `RoutineRepository.delete` (`:53-55`) is a bare `deleteRoutine`. Timed strength rules for the dead routine keep minting PLANNED rows that resolve to `RoutineGone` "Swap or unpin it in Plan" with nothing to unpin. **Fix:** `PlannerRepository.onRoutineDeleted(id)` in the same transaction (new DAO query, no schema change).

**D17 ✔ `ensureWeek` rewrites the whole week on every resume.** `generateWeek` returns `kept + generated` (`OccurrenceGenerator.kt:74`) and `PlannerRepository.kt:249` upserts all of it, twice at cold start and on every `onResume`; Room's triggers fire on the UPDATE regardless of value, so `observeOccurrences` re-emits to Home, Plan and the start sheet on every foreground, followed by one `getDeliveriesForOccurrence` per occurrence. **Fix:** upsert only generated rows; skip the reminder pass when nothing was generated.

**D18 Legacy strength sessions are attributed to a day in the device zone at read time.** `WorkoutSessionEntity` carries no zone; `SessionSummary.kt:39`, `WeekDerivation.kt:120-124`, `TrainingCalendar.kt:57` derive the civil day from `ZoneId.systemDefault()` while activities carry ADR-011's four-tuple. A Sunday 23:30 session in Los Angeles reads as Monday in Tokyo, moves `loggedEpochDays`, and sits on a different calendar day from a cardio logged the same evening. **v5 candidate:** persist `zoneId`/`localEpochDay` on `workout_sessions` at finish.

**D19 ✔ The one build anyone runs is the debug variant, and release hardening has never been exercised.** `AppLog.redactMessages = !BuildConfig.DEBUG` (`PersonalTrainerApp.kt:80`) is `false` on the phone in use, so user-authored titles and file paths reach logcat (`StartTrainingDay.kt:74`, `PreMigrationSnapshot.kt:99`, `Mappers.kt:163-174`, `DbMaintenance.kt:95`); R8 + Gson + the ProGuard file have never run on a device; and `release.yml` (`:174-213`) never archives `mapping.txt`, so a minified crash bundle from `DiagnosticRedaction` (which keeps only `com.sinura…` frames by prefix) is unreadable. **Fix:** redact by default in both variants with a debug-only toggle; upload `mapping.txt` as a release asset; `-keeppackagenames`; install one `assembleRelease` APK and walk export → restore → diagnostics before the next `v*` tag.

**D20 ✔ Four screens break the one-filled-Volt rule in the states a new user hits first.** `ThisWeekCard.kt` no-plan branch (≈205-252): a recovery Volt ("Use my answers again" or "Suggest a week") *and* a filled "Start a workout", with no `quietStart` check. `PlanScreen.kt:405-413` + `:458-466`: "Add session" Volt plus a non-compact `EmptyState` whose action is a `PrimaryGymButton("Create a routine")`. `CustomWeekScreen.kt:~340`: filled Volt dots on every filled day under a Volt confirm (`WeekStrip` solved this with check marks). `SettingsScreen.kt:842-847`: Export is `SecondaryGymButton` while ADR-014 §4 and `AccessibilityMatrix` say "Export remains the page's Volt". **Fix:** secondary Start when a recovery Volt is present; `compact = true` on Plan's empty state; check-mark fills; decide Export and correct either the code or the ADR.

**D21 First-viewport failures on the four main tabs (360 dp arithmetic from the dp values in code).** With the missed-work card up (four 56 dp buttons, ≈365 dp) the day's board and its Volt sit ≈900 dp down on **Home and Plan** — the morning after a missed week is exactly when today must be one glance away. **Body**: `PANEL_HEIGHT = 440.dp` fixed (`BodyMap.kt:291`) puts the legend at the fold and every muscle row and recommendation below it; at 360×640 the figure is cut. **History**: ≈306 dp of fixed chrome plus a ≈430 dp calendar puts the first session row at ≈770 dp. **Active workout**: content viewport ≈424 dp (≈264 on 640); the entry wells start below the fold, and after every log `setsRequester.bringIntoView()` (`ActiveWorkoutScreen.kt:828-837` ✔) scrolls the *logged-sets panel* into view, which sits under the wells, so the wells leave the screen after set 1 and the lifter scrolls back for every set. *Layout needs device check; the bring-into-view target is verified.*

**D22 ✔ Restore that fails before WIPING tells the user it is "finishing from the copy" and blocks every workout start until relaunch.** `BackupRepository.kt:201` `mark(WIPING)` throws `INTERRUPTED` on disk failure; `namedCommitFailure` (`:311-324`) reads phase STAGED and falls through to that message; the STAGED journal stays open so `WorkoutRepository.kt:82-87` refuses starts until the next recovery pass. **Fix:** clear the journal on a stage/mark failure; STAGED means "nothing changed".

**D23 ✔ Reminder notification prints the routine title on the lock screen and its Move/Skip mutate the plan without unlocking.** `ReminderNotifications.kt:57-65`: `setContentText(title)`, no `setVisibility`/`setPublicVersion`, actions without `setAuthenticationRequired`. **Fix:** `VISIBILITY_PRIVATE` + public version "Time to train"; `setAuthenticationRequired(true)` on API 31+.

**D24 ✔ Home and Plan do not know a cardio session is live.** `HomeViewModel` derives `inProgress` from `workoutRepository.observeInProgress()` alone (`:89`); the bar and the start sheet combine `activityRepository.observeLive()`. During a live run Home shows the filled "Start a workout" Volt, tappable planned rows and can raise the missed-work prompt; Start reaches `refuseIfOtherLive` → "One live activity at a time." banner (ADR-021 §2 says the Volt hides while a session is live). **Fix:** combine `observeLive()` into Home/Plan `sessionLive`.

**D25 Process death loses in-flight authoring on four screens.** `routine/new`: the created id, name, notes and staged targets never reach `SavedStateHandle` (`RoutineEditorViewModel.kt:83-92, 284, 698-705`) — after death the editor reopens empty and the next add mints a second "Untitled routine". Custom week: seven days of lifts live in plain `MutableStateFlow`s and `pendingCustomWeek` is in-memory (`CustomWeekViewModel.kt:62-75`; `AppNav.kt:469-483`). Composer lines/title/day, live-cardio distance, and onboarding step/answers are in-memory too. The workout draft is the one authoring surface that is mirrored — but `editingSetId` is not (`ActiveWorkoutViewModel.kt:180, 867-880`), so after death the LogBar says "Log" with the edited set's numbers and a tap duplicates instead of updating. **Fix:** mirror ids/text into the handle; carry custom-week answers as a nav arg or DataStore key.

### P2 — performance (X1–X3 defeat a ledger "done" row)

**X1 ✔ Every logged set re-runs the full insights compute.** `TrainingInsightsSource.assemble` (`:167-171`) combines `exerciseRepository.observeAll()` with `workoutRepository.observeLastLogged()`, whose query (`WorkoutDao.kt:388`) is an ungated `GROUP BY` over all `set_logs` including the in-progress session. Each logged set changes that exercise's `MAX(completedAt)`, `Sources` differs, and `mapLatest` runs heat + coach basis + engine + week derivation again — the "re-aggregate history while logging" the ledger says is gone. `ActiveWorkoutViewModel.suggestedLift` adds a catalog read per emission. **Fix:** finished-only recency (`JOIN workout_sessions … finishedAt IS NOT NULL`) gated on `observeFinishedWorkGeneration()` like its siblings; `distinctUntilChanged()` on `Sources`; keep the ungated variant only for picker order.

**X2 ✔ Every preference write re-emits ~30 equal-but-new values.** `PreferencesRepository` has 26 `safePreferences.map { … }` flows and zero `distinctUntilChanged`. A DataStore edit re-emits `SchedulePreferences`, `WeightUnit`, `CoachPreferences`, the lighter-week day and the rest, four of which sit inside `assemble()`'s combine, so the Body window chip (persisted) runs the full pass instead of the retarget the ledger describes, and so do a weigh-in, a rest preset, a `PendingOccurrence` bind/clear at workout start/finish, and every Settings toggle — with Home and Plan re-deriving behind them. **Fix:** a `pref()` helper that appends `.distinctUntilChanged()`; `distinctUntilChanged()` on `Sources`.

**X3 ✔ Every exercise thumbnail decodes a full 768×768 still on the main thread, per row, uncached.** `ExerciseThumb.kt` draws `painterResource(art)` at 40/56 dp; all 145 stills in `drawable-nodpi` are 768×768 (measured from the WebP headers), so each row decodes 2.36 MB of ARGB synchronously in composition, remembered only per composable instance behind a weak framework cache. Library/picker (129 built-ins), workout cards, plan rows and detail headers all pay it; `TemperMark` decodes a 768² still for an 80 dp mark in every non-compact `EmptyState`; `TemperStillCache` pins 4.7 MB of mutable bitmap for the app's lifetime for a panel that never draws it above ~230×440 px. Catalog integrity is fine (129 ids ↔ 129 keyed entries ↔ 129 files). **Fix:** a process-wide LRU that decodes with `inSampleSize = 4` on IO behind a badge placeholder, or ship 160 px row thumbs and keep the 768² stills for detail headers; sample 2 for the Body stills.

**X4 ✔ The navigation root recomposes once per second for the whole live session.** `PersonalTrainerNav` reads `liveBarViewModel.uiState` in its own body (`AppNav.kt:~269-280`); the 1 Hz elapsed label produces a new state each second, invalidating the root, the `Scaffold` bottom-bar slot and, because `goToTab` is a local function captured by un-memoised lambdas, likely the `NavHost` builder and its 19-destination graph. **Fix:** `LiveSessionBarHost` that collects internally; a `hasLiveSession` boolean flow for visibility; a remembered `goToTab` lambda.

**X5 ✔ `SharedPreferences.commit()` on the main thread on every rest start, adjust and stop — including after every logged set and on Finish.** `RestTimerStatePersistence.kt:55-63,80-82` via `RestTimerStore.publish`, called from `viewModelScope` (Main.immediate) in `ActiveWorkoutViewModel` (`:1092-1101, 964-974, 942, 907`) and `FinishWorkout.kt:193`. The durability argument (arm the alarm only after the row is on disk) is right; it does not require the UI thread. **Fix:** an ordered IO job in the controller: publish snapshot → persist → arm → sync service.

**X6 ✔ `PlanDayScreen` creates a second `PlanViewModel`** (`PlanDayScreen.kt:68`) scoped to its own back-stack entry, doubling the twelve-flow Plan pipeline while a day page is open, and racing the one-shot `pendingWeekSuggestion`/`pendingAnswerReplay` consumers in `init`. **Fix:** a thin `PlanDayViewModel`, or scope to the tab entry.

## 5. Front-end design plan — what was missed
