## Behavior contracts

**Policy (plain JVM):** API 26/30 always attempt Exact whether or not a
grant flag is set. API 31/34/35 attempt Exact only when
`canScheduleExactAlarms` is true; otherwise BestEffort.

**Plan (plain JVM):** missing AlarmManager, remaining ≤ 0, or a missing
PendingIntent is Failed. Exact attempt that succeeds is Exact. Exact
attempt that fails and inexact succeeds is BestEffort. Both failing is
Failed.

**Scheduler (Robolectric, recording capability):** granted → only
`setExactElapsed`. Denied on API 35 → only `setInexactElapsed`. API 30
attempts Exact even if the grant flag is false. Exact throw falls back
to inexact. Both throwing is Failed. Remaining ≤ 0 and a missing
AlarmManager do not arm. Refresh after grant reschedules a live timer
as Exact.

**Settings / onboarding / workout:** configuring rest or starting rest
marks exact-alarm prompt eligible. BestEffort + eligible offers the
settings intent. BestEffort without eligibility does not. Applying the
onboarding plan does not mark eligible.

**Instrumented (API 29):** a live rest reports Exact. The debug APK
declares `SCHEDULE_EXACT_ALARM` and does not declare `USE_EXACT_ALARM`.

## Production change

`SCHEDULE_EXACT_ALARM` is declared. `USE_EXACT_ALARM` is not.
`setAlarmClock` is gone. Exact APIs run only when
`ExactAlarmPolicy` says they may, and
`AndroidExactAlarmCapability.setExactElapsed` re-checks
`canScheduleExactAlarms()` in the same method. Failures are logged.
The UI copy is "Rest alerts may be delayed", never "reliable".
`MainActivity.onResume` rechecks the grant and reschedules a live
timer. The two exact-alarm `MissingPermission` baseline entries are
removed.
