# Verification: every P1 and P2 claim, refuted or confirmed

Part of the [25 September whole-app audit](AUDIT.md) (packet X6). Six verifiers, one per area cluster, were given the specialist passes' P1/P2 claims and told to refute them from the code at `1ad3b11`. Each row says what was read, what was run, and whether the severity the pass proposed stands. Runnable claims became JUnit probes whose assertion states the defect, so a green probe confirms the claim; all probes ran once on the JVM (last section). Claims only a phone can settle are marked Needs runtime and are listed in the record under "To confirm on the phone".


Rows examined across the six clusters (every P1/P2 claim, the rows merged as duplicates, and the P3 spot-checks): **57 confirmed**, **3 partly** (claim re-worded, severity unchanged), **0 refuted**, 13 merged as duplicates of another row, 0 needing the phone. Severity arbitrations: eight claims were argued up or down; every one stayed at P2 except one downgrade to P3 (`DB-1 (B7)`: a deleted custom lift's sessions keep their own snapshot, so nothing goes blank). No pass and no verifier rated anything P1; the record says why the closest candidates stay P2.


Two rows were verified by the lead rather than a verifier: `UI-17 (B10a)` (History goes blank and the process dies when the activity-history read throws) is proven by the render harness run itself, whose failing DAO decorator escaped `HistoryViewModel.kt:189` uncaught in all four History error methods; and `BR-3 (B14)` is the same lane failure as `TS-2 (B13b)`, which V4 verified and named the survivor.

### Refutations

**B1 S-13, one example only (the finding itself stands and folds into B3 S-12).** The row says "a routine
lift switched from a hold back to reps (`targetSeconds = null`) stays a hold on every other phone". There
is no such switch on the phone that would make it. `RoutineRepository.updateExercise`
(`P/data/repository/RoutineRepository.kt:154-172`) computes
`val hold = current.item.targetSeconds != null || targetSeconds != null` and then
`targetSeconds = if (hold) HoldWork.countdownSeconds(targetSeconds ?: current.item.targetSeconds) else null`,
so once a lift is a hold every later save keeps it a hold; the add path (`:105`) is the same shape, and
the only other `targetSeconds = null` in `app/src/main` is a session-lift projection
(`P/domain/Models.kt:206`), not a routine write. The mechanism the row describes is real for every other
nullable column it and B3 S-12 name (a cleared target weight, `fixed_zone_id`, `routine_id`,
`bodyweight_check_in_weekday`, `completed_activity_id`, `occurrence_id`, and `deleted_at_ms` on a
re-created row), and `claim_S_12_B3_holds` pins the `target_weight_kg`, `target_seconds` and
`deleted_at_ms` omissions on the wire. Only the hold-to-reps sentence is dropped.

No other claim in this cluster could be refuted. What I looked for and did not find: a per-row catch or
cursor-per-page in `pullTable` (S-12 B1, S-11 B1); a `serializeNulls()` or `Prefer: missing=default` on
the sync writer (S-12 B3); a cursor reset, an enrolled-id check or a user-id column on local rows (S-14
B1, S-11 B3); a second caller or a scoped variant of `deleteAllRows` (S-12 B2); a timeout, `disconnect()`
or dispatcher hop in `SupabaseRestClient`/`SupabaseSyncRemote` (S-11 B2); a `RestException` mapping or a
message-stripping sink in `AppLog` (PV-2); a wait for `LoadingFromStorage` to settle or a
`runAttemptCount` cap in `SyncWorker` (S-11 B7); a signed-in-offline state for `NetworkError` (PV-3);
a clamp on the watermark or a server trigger on `updated_at_ms` (S-13 B3). The tests that touch these
paths (`SyncEngineTest.kt:246-274`, `SyncPullInPlaceTest.kt:283-293`, `SyncPlanRemoteRowsTest.kt:27-46`,
`AccountCoordinatorTest.kt:108-152`, `AppLogRedactionTest.kt:33-42`) pin the neighbouring behaviour, not
the defect, in every case.

### Noticed, not verified

- `SyncAuthoring`'s single-row hooks (`onActivitySessionCommitted`, `onActivityDeleted`, `onRoutineDeleted`,
  `onRoutineExerciseRemoved`, `onCustomExerciseDeleted`, `onGoalUpserted`, `onGoalDeleted`) drop the edit
  for good when `auth.session.first()` reads null (the PV-3 `NetworkError` window and the B7 S-11
  `LoadingFromStorage` window); the whole-table hooks recover on the next edit. ADR-031 decision 3's
  enrolled-id bullet is the planned fix, and it should name these hooks.
- `SyncCopy.ownerFacingError` maps any message containing "403" to "Cloud access was denied. Sign out and
  sign in again." — for the B3 S-11 refusal that advice makes it worse (signing in again re-queues the
  same row).
- `AuthImpl.signOut` (gotrue-kt 2.6.1) swallows a `RestException` only for a fixed status list read from
  a `List.contains` over constants I did not decode; the pass's "sign-out swallows `RestException`" is
  true only for that list. A 5xx or gateway reply on sign-out is rethrown and reaches `AppLog.e`.
- Once a routine lift is a hold it cannot go back to reps through `RoutineRepository.updateExercise`
  (`:155`); whether the routine editor offers that switch at all is a screen question outside this
  cluster.
- `SupabaseAccountAuth.deleteChildTablesFirst` makes 17 blocking HTTP calls with no dispatcher hop from
  `viewModelScope` when deletion is re-enabled (B2 already notes this as the main-thread half of S-7).
- The B2 S-11 probe cannot flip on a fix that uses DriveHttp's 20 s/30 s values (see Probes); when S1
  adds the timeouts, the pin should be a small `HttpURLConnection` factory seam or a read of the
  configured values, not a wall-clock test.

  hung read cannot keep the Gradle worker alive; `@After` closes the socket, which resets the pending

- `claim_S_12_B3_holds` → B3 S-12 (and B1 S-13, folded). Pure JVM. Expected on trunk = **passes**

### Refutations

**DB-1 (B7) is Partly, not Confirmed, and P3 rather than P2.** The uncounted table is real: `usageFor` (`ExerciseRepository.kt:210-214`) reads three counts and `activity_blocks.exerciseId` (`ActivityEntities.kt:74`) has no foreign key, so `deleteCustom` returns `Deleted` for a lift that only activity blocks reference (`claim_DB_1_B7_holds` pins it). What the pass got wrong is the consequence. The block row is not "pointing at nothing" in any reader: `completedSessionStills` (`ActivityDao.kt:82-104`) selects `COALESCE(e.name, b.exerciseName, '')` and the same fallback for load type and equipment, and `ActivitySession.toInsightSession` (`ActivityInsight.kt:27-64`) builds the insight's `Exercise` entirely from the block's own snapshot (`exerciseId`, `exerciseName`, `loadType`, `equipment`, `muscles`) without touching the catalog, so the Body insight the pass says "has nothing to name" names it exactly as before. `CURRENT_STRUCTURE.md` lists this column among the soft keys designed to survive their parent, and B4a's DB-14 note reaches the same reading. The remaining halves — check-then-delete outside `writeExercise` and the tombstone queued at `:222` before the delete at `:223` — are the shape B4a already filed as DB-5 at P3 and the S-3 family (dormant under `AccountSyncGate.SYNC_PAUSED = true`). Nothing is lost or blanked, so I propose P3; the fix (`countBlocksForExercise` in `usageFor`, delete inside `writeExercise`) is still worth doing for consistency with the RESTRICT rule the other three tables enforce.

**UI-3 (B10b) is P2, not a "protect data" P1.** What one tap loses is the current `training_blocks` row and its DataStore mirror (`PreferencesRepository.kt:569,583-584`): one start date and a week count. No `workout_sessions`, `set_logs`, routine or routine exercise is deleted — `OnboardingApplier` adds alongside (`:34-38,111`) and `beginBlock` touches nothing but the block. The block is exported in every backup as `preferences.blockStartEpochDay`/`blockWeeks` and `pastBlocks` (`AuthoredInventory.fromDocument:61-62` counts it), so a Drive or file backup from before the tap restores it, and the duplicate routines are visible in the list and deletable. The user-facing cost is "week 4 of 12" becoming "week 1 of 12" plus a second Upper/Lower to tidy — annoying and silent, but recoverable and not history. The fix is the caption and confirm the other door already has (`PlanSetupCopy.kt:11-13`).

**BK-3 (B5) is P2, not a "protect data" P1.** The blind spot is real and the probe wipes a goals-and-rules phone through `prepareRestore` → `commitRestore` with no refusal. But `commitRestore` (`BackupService.kt:261-266`) always takes `localBackupRepository.createSnapshot()` and writes it as a verified safety copy before anything is staged, and that snapshot is the full document — `LocalBackupRepository.kt:285-290` includes `activityTemplates`, `scheduleRules`, `scheduleOccurrences`, `missedWorkDecisions`, `reminderDeliveries` and `measurableGoals`. `SafetySnapshot.verify` compares only the eight-table inventory, so it cannot *detect* a dropped goal, but it also cannot drop one: the JSON on disk carries them. The safety copy is listable and restorable from Settings (`BackupCoordinator.kt:612-624`, B5 §1), and restoring it back onto the now-empty phone passes the same guard in the safe direction (`incoming.isEmpty && !local.isEmpty` is false). So the loss is silent and recoverable, which is P2. The three-copy retention is the only clock on that recovery.

**L-3 (B9a) / DB-2 (B4b) are P2, not a "first-run blocker" P1.** The rubric's first-run blocker is a healthy install that cannot get past its front door; this needs a `user_settings.preferences_pb` that no longer parses. DataStore writes through a scratch file and rename, so a torn write cannot produce that; it takes filesystem damage, and no crash record or owner report shows it. When it does fire the picture is as bad as both passes say (`claim_DB_2_B4b_holds`: gate Unavailable, chooser input "not chosen", every edit throws, Retry can never succeed), and the only exit — clearing app storage — takes the Room history with it unless a Drive copy exists. That is why it heads P2 rather than sits in it. The fix is not mechanical: a `ReplaceFileCorruptionHandler { emptyPreferences() }` would make the app look like a first install, which `DataHealthCopy.SETTINGS_BODY` ("This is not a first install") was written to prevent, so the owner has to choose between "reset settings and say so" and "keep the gate, hide the chooser, and offer export". One row, two layers.

### Severity arbitration (asked by the lead)

**UI-2 (B11): P2, not P1.** The rubric's P1 is "protect data or a first-run blocker". Nothing stored is lost or changed: `FinishWorkout` writes `finishedAt` and clears the draft; the set keeps the values it was saved with, and History's `SetEditSheet` can still correct it afterwards. What is discarded is an unsent correction plus the lifter's intent, without a word — a real defect, and a cheap one (`canFinish` gaining `editingSetId == null`, as the dock's `WorkoutPrimaryAction.kt:153` already does, plus one dialog line). If the owner reads "protect data" as "never drop typed input silently", it moves to P1; on the rubric as written it is P2.

**The four AX rows: P2 stands — but not "against ADR-026's accessibility paragraph".** ADR-026 (`docs/architecture/ADR-026-frontend-redesign.md`) contains no accessibility paragraph; `grep -il accessib docs/architecture/*.md` does not list it, and its only touch is decision 6 ("The day picker may scroll to preserve touch targets"). The sentence B12 quotes — "proper roles/groups, no repeated decorative descriptions or tick announcements, focus restoration, accessible map/menu alternatives, measured contrast, no clipped essential values" — is `docs/FRONTEND_REDESIGN.md:232-235`, the F11 acceptance paragraph, with the 48 dp rule at `:105` and ADR-023 decision 2 for the colour-only channel; ADR-005 says only "Contrast and TalkBack are required". Against those, each row is a defect in a promised behaviour on a screen a screen-reader user must be able to complete (UX25-AC01, `docs/ux-program/UX-Acceptance-Matrix.md:211`, lists set edit, routine create and history correction). None loses data or blocks first run, so P2 is right; the record should cite FRONTEND_REDESIGN F11 rather than ADR-026.

## Probe run

The six probe files were copied under a temporary `audit` test package, run with `./gradlew -PskipStaticChecks testDebugUnitTest --continue --tests 'com.sinura.personaltrainer.audit.*'` on JDK 17, and deleted; nothing under `app/` ships. Their sources are kept as `evidence/probes/AuditProbe*Test.kt.txt` so a fix packet can flip the one it closes. Green means the defect the probe asserts is present at `1ad3b11`; red means the assertion did not hold, and the note below says what that means for the row.

The first run (04:46 UTC) wedged after nine minutes on `claim_S_11_B2_holds`. The probe called `SupabaseRestClient.getUpdatedSince` against a local socket that never answers, under `@Test(timeout = 5_000)`; JUnit's timeout interrupts the thread, but a blocking `HttpURLConnection` read ignores the interrupt, so the run never came back. That is the S-11 defect in one line: no timeout on the sync transport, and no way to cancel it. The probe was rewritten to make the call on a daemon thread, assert it is still blocked three seconds later, and close the listening socket to release it. The second run (04:55 UTC, 34 s on the warm daemon) is the one recorded below: **34 probes, 33 green, 1 red**.

The one red, `claim_UI_3_B9b_holds`, failed on its third assertion only. It seeded the guided launch with LBS and asserted the restored week did not write LBS, but LBS is also what the store answers when nothing is saved (`WeightUnit.fromStorage(null)`), so the assertion could not tell "never written" from "written". Its first two assertions held: the goal and the typed bodyweight are dropped after process death. The unit clause stands on the code (`CustomWeekViewModel.pendingWeightUnit` lives only in memory and is written at confirm), so the row stays Confirmed.
