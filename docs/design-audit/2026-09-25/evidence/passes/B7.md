### Notes on §2

**RM-1.** The commit:

```kotlin
// P/update/DebugApkInstaller.kt:82-87
val status = Intent(context, MainActivity::class.java)
    .addFlags(Intent.FLAG_ACTIVITY_NEW_TASK)
val flags = PendingIntent.FLAG_UPDATE_CURRENT or
    if (Build.VERSION.SDK_INT >= 31) PendingIntent.FLAG_MUTABLE else 0
val pending = PendingIntent.getActivity(context, sessionId, status, flags)
session.commit(pending.intentSender)
```

`MainActivity.onNewIntent` (`:109-117`) reads only the rest-session, occurrence, review and
delivery extras; `onCreate` (`:33-51`) the same. Android's contract for a session committed by
an app without install privileges is to deliver `STATUS_PENDING_USER_ACTION` with the
confirmation activity in `EXTRA_INTENT`, which the app must `startActivity`; `:72-74` even
sets `USER_ACTION_REQUIRED` on API 34+. Nothing launches it, so the session sits open.
`DebugUpdateMonitor.runInstall` (`:111-118`) publishes `Installing` and then `Idle` as soon
as `installer.install` returns, so the banner reads "Android will ask you to install this
update" (`P/domain/DebugUpdateCopy.kt:19`) for a moment and reverts to "Update"; every tap
opens another session and none is abandoned. The offer is unchanged (`refresh` `:132-153`),
so the banner keeps coming back. Counter-evidence looked for: the grep above across
`app/src/main`, `app/src/debug` and `app/src/test`; `DebugUpdateInstallTest.kt:185-204`
replaces `DebugApkInstaller` with a fake whose `install` only records the file, so no test
reaches `commitSession`. Not P1: no data is touched and Obtainium (SETUP.md §7) remains the
owner's lane. Fix shape: read the status in `MainActivity` (or a dedicated `getBroadcast`
receiver), launch `EXTRA_INTENT` on `STATUS_PENDING_USER_ACTION`, publish `Failed` on
`STATUS_FAILURE*`, delete the staged file on success (see RM-7).

**S-11.** The worker:

```kotlin
// P/data/sync/SyncWorker.kt:14-21
val app = applicationContext as? PersonalTrainerApp ?: return Result.success()
val coordinator = app.container.syncCoordinator
val session = app.container.accountAuth.session.first() ?: return Result.success()
if (!app.container.accountAuth.configured) return Result.success()
return coordinator.runPass(session.userId).fold(
    onSuccess = { Result.success() },
    onFailure = { Result.retry() },
)
```

`session` is `client.auth.sessionStatus.map { … LoadingFromStorage -> null … }`
(`SupabaseAccountAuth.kt:32-45`), so `first()` returns the current status without waiting for
loading to finish. The concrete window is a process WorkManager starts itself: the auth client
begins in `LoadingFromStorage`, the pass reports success and is gone, and under
`APPEND_OR_REPLACE` nothing re-runs it until the next local change. `SyncEngine.run`
(`P/data/sync/SyncEngine.kt:37-51`) turns a push or pull exception into `failure`, so a
persistent server error retries on WorkManager's default exponential backoff for ever.
`PersonalTrainerApp.onCreate:147-150` only requests a pass after `session.first() != null`,
which is the same non-waiting read. S4 fix shape: `PersonalTrainerApp : Configuration.Provider`
with a `WorkerFactory` that hands `AppDependencies` to `SyncWorker` and `ReminderWorker`
(and removes the `WorkManagerInitializer` node from the manifest); in `doWork` wait for a
non-loading status with a timeout and `retry()` while loading; `setBackoffCriteria` plus a
`runAttemptCount` cap that returns `failure()` and writes S1's quarantine row so the head
cannot block the chain.

**DB-1 (B10a hand-off, taken here).** `usageFor` (`ExerciseRepository.kt:210-214`) reads

with `val exerciseId: String?` and no `ForeignKey` (CURRENT_STRUCTURE.md:194-198 lists it among
the six soft keys). `deleteCustom` (`:216-225`) does not use `writeExercise` (`:227-230`), so

name is cancelled; `cancelForOccurrence` (`P/reminder/WorkManagerReminderScheduler.kt:43-46`)
is the belt that also dismisses the card. Callers checked: `markOccurrenceDone` (`:363`),
`skipOccurrence` (`:384,:391`), `moveOccurrenceForward` (`:515,:528`), `moveOccurrenceToDay`
(`:580`), `setRuleHour` (`:142`), `applyDayOrder` (`:185`), `retireOrDeleteRuleLocked`

harmless: `ReminderPolicy.decide` (`P/domain/ReminderPolicy.kt:37-40`) returns `STALE` for any
non-PLANNED occurrence, pinned by `ReminderReceiversAndWorkerTest.workerDoesNotNotifyAStaleOrMissingDelivery`
and `ReminderPolicyTest.completedOccurrenceIsStale`. `applyMissedWork` (`:340`) deletes removed
occurrences without cancelling their work, but the rows cascade
(`P/data/local/entity/PlannerEntities.kt:68-76`, `onDelete = CASCADE`) and the orphan job then
finds no row (`:428`). What is not pinned is the work-name step itself: see RM-7.

**Hash codes and `PendingIntent`s, mostly ruled out.** Occurrence ids are
`occ-<ruleId>-<epochDay>` (`P/domain/OccurrenceGenerator.kt:12`) with a UUID in the rule id
(`PlannerRepository.kt:212`); a 32-bit `String.hashCode()` collision between two live
occurrences is negligible. The broadcast codes `(action + occurrenceId).hashCode()`
(`P/reminder/ReminderNotifications.kt:196-212`) differ per action; the review code
`occurrenceId.hashCode()` and the Start code `("start" + occurrenceId).hashCode()` carry
different actions, so `filterEquals` separates them anyway. The seven day alarms use request
codes 0–6 against `WorkoutAlarmReceiver` (`P/reminder/WorkoutAlarmScheduler.kt:89-96`); the rest
alarm uses 30 against `RestTimerAlarmReceiver` (`P/timer/RestTimerAlarmScheduler.kt:127`);
different components, no clash. `RestTimerNotifications.openAppIntent` uses code 20 on a
bare `MainActivity` intent (`P/timer/RestTimerNotifications.kt:191-202`) and the installer uses
`sessionId` on the same shape (`DebugApkInstaller.kt:82-86`); session ids are random ints, and
the mutability flag differs, so treated as negligible. The one real overlap is RM-5.
