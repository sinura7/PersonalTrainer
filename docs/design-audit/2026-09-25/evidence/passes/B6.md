### Notes on §2

**RT-1.** The three custom views are the whole visible countdown: `setCustomContentView(compact)`, `setCustomBigContentView(expanded)`, `setCustomHeadsUpContentView(expanded)` at `RestTimerNotifications.kt:163-165`, and `DecoratedCustomViewStyle()` at :166 lets SystemUI draw the header and the background from the *system* theme. Both layouts set `android:textColor="@color/rest_notification_text"` / `@color/rest_notification_kicker` with no `android:background` (`notification_rest_running.xml:2-10`); `values/colors.xml:7-8` give `#F2F5F7` and `#9BA7AE`; `values-night/colors.xml` holds only `window_background`. Counter-evidence looked for: a theme attribute (`?android:attr/textColorPrimary`) — none; a night qualifier — none; a test that renders the RemoteViews — `RestTimerNotificationsTest.kt:42-65` reads extras only. The app's own comment at `MainActivity.kt:52-55` ("a phone in light mode got dark status icons on a near-black window") shows the owner's phone has run in light mode, so this is not hypothetical. Font scale is a separate, `R` item (§3 RT-9).

**RT-2.** `RestNotificationGate.kt:55-65`: `LaunchedEffect(Unit) { if (SDK >= 33 && !decided) { if (!granted) showWhy = true } }`; `decided` and `showWhy` are `rememberSaveable` (:47-48), scoped to the back-stack entry. Nothing writes a preference: the only persisted prompt flag in `P/data/repository/prefs/` is `LAUNCH_PERMISSIONS_ASKED` (`SettingsStore.kt:106`), read by the first-open walk alone (`AppNav.kt:320,362`). So the sequence on a denied phone is: walk asks once (persisted) → every later workout entry (`ActiveWorkoutScreen.kt:221-222`, override is test-only) and every rest page (`RestTimerScreen.kt:84`) shows `ConfirmActionDialog` (:67-85) until granted. The doc block at :29-39 says the opposite ("Asks for POST_NOTIFICATIONS once … Not now leaves the compact recovery row as the way back"). The recovery row itself is fine and tested (`WorkoutDockTimerRenderTest.kt:365-367`, `RestPageFitRenderTest.kt:120-122`); it is the modal that repeats. No test covers the dialog's repeat (`T/domain/RestNotificationCopyTest.kt` checks copy only).

**RT-3.** `LaunchPermissions.nextStep` (`:49-59`) returns `NOTIFICATIONS` on API ≥ 33 when not granted, then `EXACT_ALARM` on API ≥ 31 when `canScheduleExactAlarms()` is false, then `BATTERY`; `LaunchPermissionsHost` mounts it (`AppNav.kt:360-364`) once `walkMayShow(postureChosen, onTabAwayFromSettings, …)` is true (`LaunchPermissions.kt:42-47`), i.e. straight after the chooser. `continueExactAlarm` (`LaunchPermissionsHost.kt:98-103`) opens the system special-access page. Counter-evidence looked for: a `restAlarmEligible` gate (that gate exists, but only for Settings — `SettingsViewModel.kt:122-127`, set by `RestCommands.kt:113` and `ActiveWorkoutViewModel.kt:2269`); a `BuildConfig.DEBUG` gate — none in `AppNav.kt`, `LaunchPermissionsHost.kt` or `LaunchPermissions.kt` (its comment "for Temper Debug" is not enforced); an ADR amending §4/§13 — ADR-028 §2 (:26-37) only says where in first launch the walk sits. The walk is the same code path the 22 Sep L-2 fix (Q1) moved, so the owner has seen it; what has not been decided is which rule wins. The walk's EXACT_ALARM copy (`LaunchPermissions.kt:22-23`, "Workout reminders and rest alerts stay on time when this is on") is true of the code but not of ADR-012 §9 — §4, for B7.
