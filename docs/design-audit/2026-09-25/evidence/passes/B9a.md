### Notes on §2

**L-3.** Chain, all `C`: `PreferencesRepository.kt:85-87` builds `preferencesDataStore(name = "user_settings")` with no corruption handler, so a corrupt file throws `CorruptionException` (an `IOException`) from `data` on every read. `onboardingCompleteHealth` (:430-441) uses `observeHealth` on the raw `dataStore.data`, so the gate becomes `UNAVAILABLE` (`OnboardingGateViewModel.kt:56-60`) and `PersonalTrainerNav` returns the retry `EmptyState` (`AppNav.kt:300-312`). `SettingsStore.safePreferences` (:46-53) catches the same `IOException` and emits `emptyPreferences()`; `savePostureState` reads through `store.pref` (`SavePosturePrefsStore.kt:24-28`), so it reports `chosen = false`. `ensureLegacyMigrated` (:39-49) returns early only when `chosen` is true; with all-default inputs `inferLegacySavePosture` returns null (a fresh pattern), so `_savePostureReady` flips true (`SettingsViewModel.kt:198-204`) and `needsChooser` (:488) is true. `MainActivity.kt:93` composes `SavePostureHost` beside, not inside, `PersonalTrainerNav` (:74-81), and :72 clears the semantics of everything beneath. Counter-evidence looked for: a `corruptionHandler` (none, grep over `app/src/main`); a try/catch in `chooseSavePosture` (none, :206-210); a test with a throwing store (`OnboardingGateViewModelTest:95-107` tests only the pure `gateFromHealth`). The `DataHealthCopy.SETTINGS_BODY` copy "This is not a first install" (`domain/DataHealth.kt:55-56`) says the app already decided this case must not look like a first install; the chooser on top says the opposite.

**UI-1.** `ReminderHandoff` (`AppNav.kt:235-242`) and its doc say reminder taps "always land on Home first" — deliberate for the tab case, never considered for a pushed screen. `goToTab` is `popUpTo(start){saveState}` (:411-413), so a pushed screen above Home is popped, and by Navigation's keying (UI-9) it is not restored. `MainActivity.kt:51` / `:116` call `consumeStartedDelivery` on every Start launch before Home has run `startOccurrence`; `markDeliveryStatus(STARTED)` cancels the scheduler for that delivery (`PlannerRepository.kt:498`), so a `Blocked` outcome (`HomeViewModel.kt:452-457`, then `ResumeOrDiscardDialog` → Resume) or `Missing` (:412-415) leaves a delivery that says STARTED for a session that never started and cannot be snoozed. Counter-evidence: `DailyAgendaCard.kt:184-188` does print "Finish or discard the live session first." on Home, so the ejection is explained once you look; and `HomeViewModelTest.reminderReviewOpensConfirmAndStartsNothing` / `reminderStartStartsTheOccurrence` (:262-281) pin the non-live path only. Data is never lost (the floor's session is persisted; the occurrence stays PLANNED), which is why this is P2, not P1.

**UI-12.** Asked by the coordinator on B4b's behalf: does a throwing read in the bar's strength branch crash or degrade? The read degrades. `FinishWorkout.kt:49-52` wraps `getSession` and :58-65 wraps the finish write in `runCatchingCancellable`, returning `FinishOutcome.Failed`, which `CompleteTraining.finishWorkout` (:43-44) maps to `Failed` and the bar renders (`LiveSessionBarViewModel.kt:242-245`); `DiscardWorkout.kt:31-37` likewise. What is not guarded is the follow-up write: `applyFinishOutcome` (:229-236) calls `PendingOccurrence.complete` before setting `_finishedNavigation`; `complete` (`PendingOccurrence.kt:66-72`) calls `plannerRepository.markOccurrenceDone` (`PlannerRepository.kt:354-365`, a `dao.upsertOccurrence` with no catch) and then `write(deps, null)` → `setPendingOccurrenceId` (`PreferencesRepository.kt:176`, a DataStore `edit`). `finishFromBar` (:206-225) wraps only the ACTIVITY branch (:210-214); the strength branch (:216-221) is bare. `discardFromBar` (:249-279) has the same asymmetry: the ACTIVITY branch's comment (:253-255) says exactly why it was wrapped — "an unhandled throw here took the whole process down" — and the strength branch's `forgetIfSession` (:269) is one step past `discardWorkout`'s guard. `viewModelScope` has no `CoroutineExceptionHandler` (`AppViewModel.kt:20-30`; the app's handler at `PersonalTrainerApp.kt:26-29` is on `applicationScope`), so the throw reaches `Thread.setDefaultUncaughtExceptionHandler` (:173-186), is recorded, and the process dies. Consequence: the session is already `Written`/`Discarded` (data safe), the plan row stays PLANNED so Home lists it under Still open, and the summary never opens. Counter-evidence: `LiveSessionBarViewModelTest.finishFromBarPreservesNotesStopsRestAndEmitsOneShotNavigation` (:109-136) and `discardFromBarDeletesZeroSetSessionAndDraft` (:208) run over a healthy in-memory Room, so they cannot see it. P2 rather than P1 because nothing already saved is lost; P2 rather than P3 because it is a crash reachable from every screen and leaves the plan wrong.
