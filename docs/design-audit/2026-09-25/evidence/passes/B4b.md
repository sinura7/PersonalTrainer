### Notes on §2

**DB-1.** `TrainingInsightsSource.kt:112` is `CoroutineScope(SupervisorJob() + computeDispatcher)`; `shareAssembled` (123-129) collects `assemble()` there. Compare `ActivityRepository.kt:92-104`, which puts `observeHealth` *before* its `shareIn` on the same kind of scope, and `PersonalTrainerApp.kt:26-29`, whose scope carries a handler for exactly this reason ("a single SQLite failure inside seeding… took the whole process down"). Counter-evidence looked for: `TrainingInsightsSourceTest` has `hintFailureIsolatesToProgression` (275) and `computeRunsOffMain` (285) but no test where a repository read throws (`grep throw` in that file is empty). `cachedHints` (247-269) is guarded; `compute` degrades per stage inside the calculator; the four raw upstreams are the gap. The raw variants exist because the History screen wants the `*Health` twins separately (`WorkoutRepository.kt:158-159`, `ActivityRepository.kt:126-127`); the insights pipeline picked the raw ones.

**DB-2.** `preferencesDataStore(name = "user_settings")` at `PreferencesRepository.kt:85-87` takes no `corruptionHandler`; `grep -rn corruptionHandler app/src/main` is empty. `SettingsStore.safePreferences` (46-53) turns an `IOException` into `emptyPreferences()`, which is why reads look fine. Writes go through `store.data.edit { }` (every `*PrefsStore`), which re-reads the file and throws the same `CorruptionException`. `onboardingCompleteHealth` (430-446) deliberately bypasses `safePreferences` so an unreadable store is `Unavailable`, and `ui/onboarding/OnboardingGateViewModel.kt:43` gates on it with `DataHealthCopy.SETTINGS_BODY` ("Retry. This is not a first install."). The `R` part is only how often a DataStore file is corrupt in the wild (it writes via scratch file and rename, so this is rare); the code path once it is corrupt is `C`. B10 owns what the gate screen offers; this row is the repository-side cause.
