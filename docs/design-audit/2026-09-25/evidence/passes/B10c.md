### Notes on §2

**UI-1 (arithmetic, 360 dp wide, font 1.0).** Root: `OnboardingHeader` ≈ 56 dp + `space4` 16. `PlaceStep` (`:291-335`, `spacedBy(sectionGap = 28)`): `QuestionTitle` = title 20 + 8 + `STEP_BLURB` (≈100 chars at 14 sp on 328 dp → 3 lines × 20) = 88; four cards each `cardPadding` 16 + 20 + 4 + 20 + 16 = 76 (`Metrics.kt:35`, `Type:94,110`), with 3 gaps = 388; `mixCaption` for gym-only is `STEP_BLURB` again ≈ 48; `PrimaryGymButton` = `Metrics.control` 56 (`GymButtons.kt:61`, `Metrics.kt:89`). Sum ≈ 56+16+88+28+388+28+48+28+56 = **736 dp** against ≈ 570–616 dp usable on a 640 dp screen. Counter-evidence looked for: a scroll modifier on the root (`:98-103`, none), on `PlaceStep` (`:291`, none), `imePadding`/`weight` tricks (none), and a render test of `OnboardingScreen` (none — `app/src/androidTest/.../ProductionScreensPassInstrumentedTest.kt:281-356` mounts composer, live cardio and detail only; `ui/onboarding` tests are ViewModel tests plus `BodyweightWheelRenderTest`, which renders the wheel alone). `BodyweightStep` at font 2.0 is the same shape: a 76 sp hero numeral (`Type:76`), a 144 dp wheel (`BodyweightWheel.kt:155`), two 56 dp buttons and a four-line blurb. Not P1 because guided setup is not on the forced first-run path (F8c) and Back still works.

**UI-2.** `LeaveCardioDialog.onLeaveRunning` and the dock's `Leave running` both call `onExit` (`LiveCardioScreen.kt:80-83,115`), which is `navController.popBackStack()` (`AppNav.kt:695`). `SavedStateHandle` belongs to the popped `NavBackStackEntry`, so `inputs.read()` (`LiveCardioViewModel.kt:79-81`) is null on the next entry and `loadAndTick` takes type/indoor from the Room block (`:270-273`); the Room block is what `StartLiveCardio` wrote at start (`workout/StartLiveCardio.kt:102-115`: the scheduled type, `indoor = false`, no distance), and the ViewModel deliberately never writes the draft to Room (`:74-77`). `finishActivityFromBar` (`LiveSessionBarViewModel.kt:182-204`) copies only `elapsedSeconds` onto those blocks. Counter-evidence: `recreationKeepsTheChangedInputs` (`LiveCardioViewModelTest:162`) reuses the **same** handle, which models process death, not a pop; no test covers leave-and-return. The bar's one-tap Finish with no confirm (`LiveSessionBar.kt:224-231` vs Discard's confirm `:246-258`) is B9a's — see §4.

**UI-3.** `CustomWeekLaunch.kt:7-8` explains the in-memory hand-off as protection against an Activity recreation dropping a lambda; it does not survive the process. `CustomWeekScreen.kt:84-86` is `LaunchedEffect(preferredDays, answers, pendingWeightUnit) { seedFromGuided(...) }`, which runs again on the restored entry with `launch == null`, overwriting nothing useful because the ViewModel was also recreated with `guidedAnswers = null` (`CustomWeekViewModel.kt:196-202` are plain fields, not saved state; the draft store keys are only `customWeek.selectedDay/userPicked/days`, `SavedStateCustomWeekDraft.kt:104-106`). The Onboarding entry underneath still holds the encoded answers (`OnboardingViewModel.kt:403-406`) but nothing reads them across the fork. `OnboardingApplierTest:315 aCustomWeekFromGuidedKeepsTheQuestionnaire` pins the happy path only. Fix shape (for B9b): persist the launch in CustomWeek's own `SavedStateHandle` via `OnboardingAnswers.encodeDraft`, which already exists for exactly this (`OnboardingAnswers.kt:341-345`).

**UI-4.** `ActivityReceiptHero` (`:294-359`) and `ActivityMetricTiles` (`:361-427`) are the whole top of the page; `ActivityDetailHeader` (`:233-253`) passes `title` only, no `subtitle`. `ActivitySession.performedStart` carries `localEpochDay`, zone and offset (ADR-011 §1), so the data is there. The celebration variant has no header at all (`:137-145`), so the Done receipt also lacks the day.

**UI-5.** Readers of the stored focus: `grep -rn TrainingFocus` outside `domain/` and `ui/onboarding/` finds only `data/repository/prefs/CoachingPrefsStore.kt` (store), `PreferencesRepository.kt:225` (the re-seed of setup), `OnboardingApplier.kt:92,243` (writes) and `data/sync/*` — no `ui/`, `workout/` or coach reader. `questionsFor(BOTH)` is the full list (`OnboardingViewModel.kt:66-69`) and `RoutineGenerator.generate` branches only on `CARDIO` (`:432`). The preview string: `headline` returns `"Cardio logging is ready. A lift week is not generated."` (`OnboardingPreviewCopy.kt:11-13`) and the screen appends `". "` then `"${TrainingBlock.DEFAULT_WEEKS} weeks of ${it.splitStyle.displayName}."` unconditionally (`OnboardingScreen.kt:464-467`); `OnboardingPreviewCopyTest:20` pins the headline alone, not the concatenation. `cardioFocusPreviewDoesNotInventLifts` (`OnboardingFocusTest:278`) pins "no routines", which is the promise; what it does not pin is that nothing cardio is scheduled either.

## 4. Noticed, outside my scope

- **B9a (live bar):** "Finish session" for cardio is a one-tap menu item with no confirm (`ui/navigation/LiveSessionBar.kt:224-231`) while Discard confirms (`:246-258`); together with UI-2 it saves a run without the distance the owner typed on the live screen. - **B9a/B10a:** the Body/History/Plan sheet's cardio path starts a `RUN` titled "Cardio" with no type choice (`StartOptionsViewModel.kt:209-218`), unlike Home's picture cards (`HomeViewModel.kt:315-322`); ADR-021 §2's cardio path exists only on Home. - **B9b (CustomWeek):** receiving side of UI-3; fix belongs there (persist the launch in CustomWeek's `SavedStateHandle`).
- **B10b / B11 (Settings, components):** `SnapWheelColumn` (`ui/components/SnapWheel.kt:229-278`), used by the reminder wheel, has the same no-value semantics as UI-7. `ChoiceStep` rows are `InstrumentRow(selected)` + `RadioButton(onClick = null)` (`OnboardingScreen.kt:212-219`); whether `InstrumentRow` exposes a radio role is F8a's.

- **B14 (docs):** DC-1; `OnboardingScreen.kt:79` stale entry comment (F8c); `OnboardingViewModel.kt:100-102,115-117` says setup "never writes anything until Use this plan" while `retryCatalog` seeds the catalog (`:302-304`) and Back with an existing program writes `onboardingComplete` (`:260-269`) — both defensible, neither stated.
