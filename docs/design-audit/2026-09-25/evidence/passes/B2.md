### Notes on §2

**PV-3.** Counter-evidence looked for: no test builds `SupabaseAccountAuth` (needs a real
`SupabaseClient`), so nothing pins the mapping; no other consumer of `sessionStatus`. The library's
in-memory session survives `NetworkError` and `alwaysAutoRefresh` retries with `retryDelay`
(bytecode `AuthImpl.tryImportingSession`: on `RestException` → `clearSession()`; on any other
exception → log "Couldn't reach supabase… Retrying in …", set `NetworkError`, `delay`, retry).
Re-signing in from the false "signed out" screen works (a fresh session replaces the stored one) but
is needless; the harm is the queue (S-3) and the copy. `SyncWorker.kt:16` has the same blind spot at
cold start (`LoadingFromStorage` → null → `Result.success()` without a pass), noted for B1 in §4.

**S-11.** Counter-evidence: `WorkManagerSyncScheduler.kt:19` requires `NetworkType.CONNECTED`
(reduces, does not remove, half-open sockets and captive portals); `SyncCoordinator.runPass`
`:57-60` returns while paused, so there is no runtime path today. supabase-kt's own client is not
affected: `SupabaseClientBuilder.requestTimeout` defaults to 10 s and ktor's `AndroidEngineConfig`
to 100 s connect/socket (bytecode). The main-thread half of S-7 is the same defect seen from the UI:
`deleteAccount` → `deleteChildTablesFirst` runs these calls on `viewModelScope`.

**PV-2.** Which exception a failed auth call carries (bytecode `AuthImpl.parseErrorResponse` /
`checkErrorCodes`): a body with an `error_code` becomes `AuthRestException(code, msg, status)` whose
message is just the server `msg` (no headers) — this is the modern GoTrue shape, so "Invalid login
credentials" reaches `toAccountAuthError` cleanly today and "User already registered" is shown as
is on sign-up (server copy, and an email-enumeration signal that is a Supabase project setting, not
app code). A body without one becomes `BadRequestRestException` / `UnauthorizedRestException` /
`UnknownRestException`, all built with the response and therefore with `Headers:`. The bearer for
auth calls is `currentAccessTokenOrNull() ?: supabaseKey` (bytecode `AuthenticatedSupabaseApi`), so
sign-in/sign-up carry the public anon key; sign-out and a refresh at expiry carry the user's access
token. Sign-out swallows `RestException` and only logs its status code at DEBUG (bytecode
`AuthImpl.signOut`), so the app-side path that can log a user token is a refresh at expiry that
fails with a legacy-shaped error, which the library itself logs at `LogLevel.ERROR` with the
throwable through Kermit's `LogcatWriter` (default level `INFO`, bytecode
`SupabaseClient.Companion.<clinit>`), independent of `AppLog`. That trigger is R. What is C and
always on: `AppLog.kt:66` prints throwable messages unredacted (`AppLogRedactionTest.kt:33-42` pins
the free-text message only), `SupabaseRestClient` interpolates server bodies into exception
messages, and `AccountAuthCopy.kt:62` shows `Message.text` verbatim. Contrast the sync lane, which
maps before display (`P/domain/SyncCopy.kt:27-42`), and Drive, which shortens bodies
(`P/data/backup/DriveErrorCopy.kt:38-46`). Fix shape: map `RestException`/`AuthErrorCode` to
`AccountAuthError` cases and never show `Message` for a library exception; strip or bound throwable
messages in `AppLog.androidSink`; set `defaultLogLevel` on the Supabase client.

**S-12.** Gate chain: `AccountSyncGate.kt:26` → `AccountCoordinator.kt:133` → `AccountSection.kt:304`
→ `SettingsScreen.kt:477`; `deleteAllRows`/`deleteAuthUser` have no other callers (grep of
`app/src`). Not a duplicate of S-8: S-8 is the missing server policy and the pull filter; this is the
client sending an unscoped destructive filter.
