### Notes on §2

**DM-1.** Counter-evidence I looked for: (a) a hold gate on the coach card — none: `ActiveWorkoutScreen.kt:744` shows the rec whenever the entry is enabled, the draft is not a warm-up, and the reason is not `LIFT_DONE`/`EDITING`; the only hold gates in the ViewModel are the set clock (`:222–232`), `startHoldSet` (`:995`) and `startSetStopwatch` (`:1075`). (b) a `reps >= 1` filter in the DAO — `finishedWorkingSetsForExercises` filters `isWarmup = 0 AND finishedAt IS NOT NULL` only (`WorkoutDao.kt:299–302`); `lastFinishedWork` (`WorkoutRepository.kt:1046–1058`) groups those rows by session. (c) a test — `T/domain/SetMicroRecCalculatorTest.aOneRepHoldPlaceholderDoesNotInventAClimb` (:241–260) is the only hold-lift coach test, and its fixture logs the hold as `reps = HoldWork.HOLD_REPS_PLACEHOLDER` (1); production writes 0 (`ActiveWorkoutViewModel.kt:806`, `WorkoutRepository.kt:654`), so the test passes on a set that never occurs (validation gap; for the tests pass). Arithmetic, from code: `progressionFor` → `topWorkingSet(..., NONE)` picks max reps = 0 → `action(0, 1)` = HOLD → `hint.suggestedReps = 0` → `stripReason`: `step == null` → `"Keep 0 reps."` (`ProgressionCopy.kt:32`). In-session: `fromBasis` with `basis.reps = 0`, `targetReps = 1` → HOLD → `reasonCode` → `BW_HOLD` (`SetMicroRec.kt:326`) → `nextLoad` returns `0.0 to lastReps` = 0 (`:357`) → `callLine` = `"Hold 0 reps"`. First set: `firstSet` reps = `hint.targetReps` = 1 (`:209`) → `"1 rep"` with Apply. The rest page's target line comes from the same rec (`RestTimerViewModel.kt:75`). The visible rendering on a phone is not something I ran (R for the pixels), but every string above is computed in `domain` and pinned nowhere. Fix shape: either exclude `isHold` lifts from `progressionFor`/`workoutCoachSuggestion` (the coach has nothing to say about seconds) or give holds a seconds-based rung; the former is one guard and matches ADR-030's "no `× 0`" rule (`FloorStatCopy.HOLD`).

**DM-2.** Counter-evidence I looked for: (a) zone columns on the strength entity — none (`WorkoutSessionEntity.kt:21–28`: `date`, `startedAt`, `finishedAt`). (b) a docs record naming it as debt — `ADR-011` Consequences say "activity and occurrence writes already did [persist the tuple]"; `docs/FOUNDATION_PROGRAM.md:697` says P8.1 addressed "the remaining FND-039 write path" (goals and bodyweight); neither `CURRENT_STRUCTURE.md` "Known debt" nor `completed-training-convergence.md` mentions the strength session's zone, so a reader is told FND-039 is closed. (c) tests — `CivilDateTest.capturedLocalDateDoesNotMoveWhenDeviceZoneChanges` (:131) tests `CapturedCivilTime` only; `CoachRulesTest.weekAttributionRespectsTheZone` (:225) tests that `DeloadSignal` honours the zone it is *passed*, which is the reading device's. Severity P2 rather than P1: nothing is lost or written wrongly; the day a session is attributed to moves with the phone's zone. Note for B-DB/B14: the schema half (a v8+ column set, or reuse of the activity envelope) and the docs half (ADR-011 review question, FOUNDATION_PROGRAM P8.1 wording) are theirs; the domain contract that must stop taking `zoneId = time.defaultZoneId()` is mine.
