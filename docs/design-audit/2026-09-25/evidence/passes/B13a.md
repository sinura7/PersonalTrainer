### Notes on §2

**AR-1.** What I looked for that would make it false: (a) a `.catch` anywhere in
`TrainingInsightsSource.kt` — none (grep); the only guard is `cachedHints`
(`:259-264`), which covers `loadHints`, and that is exactly what
`TrainingInsightsSourceTest.hintFailureIsolatesToProgression` pins. (b)
`observeHealth` on the four inputs — `WorkoutRepository.kt:158` and
`ActivityRepository.kt:126-127` wrap them *separately* for History
(`observeSessionSummariesHealth`, `observeCompletedSummariesHealth`); the
un-wrapped originals are what `TrainingInsightsSource.kt:159,167,173,187` take.
Every other input is wrapped (`RoutineRepository.kt:26-28`,
`ExerciseRepository.kt:66-70`, `ScheduleRepository.kt:27-29`,
`ActivityRepository.kt:146-149`, DataStore `prefs/SettingsStore.kt:47`). (c) A
collector-side `.catch`: `ActiveWorkoutViewModel.kt:600-603` has one, but a
`shareIn` upstream failure is raised inside the sharing coroutine, not in the
subscriber, so that `catch` cannot see it; kotlinx routes a failed child of a
`SupervisorJob` with no handler to the thread's uncaught handler, which on
Android ends the process. Contrast `PersonalTrainerApp.kt:26-29`, whose
`applicationScope` carries a handler for precisely this reason, and
`ActivityRepository.kt:92-104`, which wraps its own `shareIn` source. The same
scope shape without a handler also sits at `ActivityRepository.kt:81` and
`timer/RestTimerController.kt:54`; those upstreams are guarded, so only the
insights scope has an unguarded source.

**AR-2.** `AppLog.redactMessages = true` at `:96` is itself redundant
(`AppLog.kt:43` defaults to `true`), so the block before the copy does nothing;
the comment at `:92-95` explains redaction, not why capture waits.
`installDiagnosticCapture` reads the last-crash file (`:165-169`) and sets the
handler; it does not touch the container, so it can run first.

**Input list for `uiState` (18 `combine` calls, `ActiveWorkoutViewModel.kt:605-717`):**
