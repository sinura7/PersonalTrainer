### Notes on §2

**BK-1.** Counter-evidence looked for: `PreferencesRepository` delegates `BackupPrefs by BackupPrefsStore(store)` with no override (`P/data/repository/PreferencesRepository.kt:153`); the only callers of `disarmAutoBackup` are the toggle (`BackupCoordinator.kt:381`) and the unopenable-secret path in the summary (`WorkoutSummaryViewModel.kt:197`); `T/ui/settings/SettingsViewModelTest.kt` `turningItOffForgetsThePassphrase` pins the toggle and nothing pins sign-out. The excerpt that decides it:

```kotlin
override suspend fun clearDriveSession() {          // BackupPrefsStore.kt:185
    store.data.edit { prefs ->
        prefs.remove(DRIVE_ACCOUNT)
        prefs.remove(DRIVE_FOLDER_ID)
    }
}
```

What the owner then sees: the toggle still on; on the next finished workout `maybeAutoBackup` opens the sealed passphrase, `authorize` asks for consent, `declineConsent` answers false, and the summary shows `NEEDS_SIGN_IN` (`WorkoutSummaryViewModel.kt:222-231`). Drive's `revokeAccess` result does not change this: `BackupService.signOut` clears local prefs whether or not it succeeded (77-80), which is drive-auth.md decision 4 as written. Seam 6 otherwise holds: token is memory-only (`DriveAuthClient.kt:34-35`), `clearToken` then `revokeAccess` (81-101), both swallowed except cancellation.

**BK-2.** Sync is paused, so this is a gap in S1's target, not a live defect. What S1's scope line covers: "restore/sign-out reset cursors". What it does not: (a) `SyncEngine.pushOutbox` (94-110) pushes `row.payloadJson` as stored, so every outbox row queued before the restore re-creates a pre-restore row on the server; (b) `onPlanDataRestored` (`AppContainer.kt:341-348`) calls six hooks — `onScheduleChanged` (`SyncAuthoring.kt:54`) and `enqueueCompletedSession` per activity are not among them, and there is no tombstone hook for the wiped rows; (c) `replaceRoom` builds `ExerciseEntity` without `updatedAtMs` (376-392) so the column takes its default `0` (`ExerciseEntity.kt:35`), and `ActivityBackupIo.replace` passes `updatedAtMs = 0L` explicitly (31); `enqueueAllCustomExercises` → `toCustomRemote(… updatedAtMs = updatedAtMs)` and `ActivityTemplateEntity.toRemote` (`createdAtMs = updatedAtMs, updatedAtMs = updatedAtMs`) put that `0` on the wire; (d) `SyncEngine`/`SyncWorker` reference neither `DbMaintenance` nor `restoreInProgress` (grep, none). The brief's question "does restore refuse while a sync pass runs?" — no; `refuseIfLive` (`BackupService.kt:559-573`) checks only a live strength or cardio session.

**BK-3.** ADR-009 §11 says the inventory counts "schedule"; when it was written (P3.2) the schedule was `schedule_slots`, which is counted; the v4 planner (`schedule_rules`, `schedule_occurrences`, P7.1), templates (P5.5) and goals (P8.2) were added to the document (`BackupDocument.kt:26-38`) without extending the inventory. `AuthoredInventoryTest` (6 tests) asserts customs, weigh-ins and blocks only; `RestorePrepareTest.catalogOnlyFileIsRefusedAndLeavesHistory` seeds sessions. The direction that loses data needs a phone with goals/templates/rules and no session, routine, custom lift, weigh-in or block — narrow, which is why P2 not P1. `SafetySnapshot.verify` (`SafetySnapshot.kt:56-77`) compares the same inventory, so it also cannot detect a safety copy that dropped goals or templates.

**BK-4.** `MainActivity` declares no `configChanges` (manifest grep), which the ViewModel comment (169-179) already handles for rotation; the gap is navigation away. What is cut where: leave during authorize/snapshot → no upload at all; leave during PBKDF2 or the multipart POST → those are blocking and finish on the IO thread (`R`: a coroutine cancel does not interrupt `HttpURLConnection`), so a file may land in Drive that Settings never learns about (`setLastBackup`, `verifyUploadedBackup`, `setLastVerifiedBackup` all skipped). No partial Drive file either way: `uploadBackup` is one multipart POST (`DriveRestClient.kt:60-94`). The fix direction is `applicationScope` (or WorkManager) for everything after the Activity-bound authorize.
