### Notes on §2

**UI-1.** `addSessionVolt` (`PlanScreen.kt:318-319`) depends only on proposals and the missed-work prompt, never on `selectedEpochDay < today`. `WeekCell` is `selectable(role = Role.Tab, …)` with no `enabled` gate (`WeekStrip.kt:118-121`), and `LaunchedEffect(weekStart, today)` (`PlanScreen.kt:302-307`) only clamps a selection that is outside the week. On the day page `picking` is initialised `if (startInAdd && !isPast) KIND else NONE` (`PlanDayScreen.kt:81-83`), the picker is gated `!isPast` (`:144`) and the Add button too (`:182`). Counter-evidence looked for: the rules are weekly (`PlannerRepository.addTimedRule` writes a weekday rule, `:202-227`; ADR-020 §2 "Plan add is recurring"), so adding on a past *date* of this week would be a valid way to plan next week — the refusal is the screen's, not the model's. The empty-routines path is inconsistent with it: "Create a routine" calls `viewModel.buildDay(selectedEpochDay)` (`PlanScreen.kt:444`) with no past check and pins that weekday. No test pins either behaviour (grep for `PlanDayCopy.PAST`/`startInAdd` under `app/src/test` and `androidTest`: none).

**UI-2.** Compare `UI/components/WeekStrip.kt:64-80,118-121`, which has `selectableGroup()`, `Role.Tab`, `selected` and a `spoken` string per cell. `AuxiliaryPackList.kt:126-144` also uses `selectableGroup` + `selected` on its rows. The builder's strip predates both.

**UI-3.** `CustomWeekLaunch.kt:6-8` says it is held in memory "rather than stuffed into a route" for size; nothing re-arms it on restore (the only writer is `AppNav.kt:554`). `applyCustom` (`OnboardingApplier.kt:236-247`) stores goal/emphasis/equipment/age/places/focus/bodyweight only inside `answers?.sanitized()?.let`. `pendingWeightUnit?.let { setWeightUnit }` (`CustomWeekViewModel.kt:376-379`). `SavedStateCustomWeekDraft.bundleOf` (`:52-70`) writes sets/reps/rest/weight and no seconds; `liftFrom` (`:72-101`) leaves `targetSeconds` at its null default although `CustomWeekPolicy.updateTargets` (`domain/CustomWeekPolicy.kt:138-143`) does stage them. The existing process-death test (`CustomWeekViewModelTest.kt:341-365`) uses a non-hold lift and no launch seed, so it passes.

**Seam 1 premise (stated for the lead, not a finding).** The brief assumed process death mid-edit loses the editor's lift list. It does not: every picker tap writes straight to Room (`RoutineEditorViewModel.kt:1080-1089`), and typed targets live in `rememberSaveable` wells (`SessionLiftStrip.kt:507-515`) that re-stage and re-commit on restore through `LaunchedEffect(rowKey, differsFromStored)` (`:535-539`); `RoutineEditorViewModelTest.kt:932` (name, no second routine) and `:1338` (restored target still written by Save) pin it. What *is* lost after process death: open picker and its query, an open swap sheet, the Save-error caption, the Back prompt, and the paste results (`PasteUi` at `:1449-1454` is not persisted) — the "unmatched lines" list after a paste import vanishes, though the matched lifts are already on the routine (UI-7).
