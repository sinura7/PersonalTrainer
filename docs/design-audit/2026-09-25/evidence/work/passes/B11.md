### Notes on §2

**UI-1.** `rememberRestNotificationsEnabled()` (`RestNotificationGate.kt:41`) holds `decided` in `rememberSaveable` (`:48`), keyed to the composable instance; `LaunchedEffect(Unit)` (`:55-62`) sets `showWhy` whenever SDK ≥ 33 and the permission is not granted. `AppNav.kt:624-628` navigates to `Route.RestTimer` with `launchSingleTop` (a new entry each open, since the page is never already on top when tapped from the floor), and Back from the floor pops its entry (`AppNav.kt:622`), so the next entry from Home is new. Counter-evidence looked for: no preference key records the decision (`LaunchPermissionsHost.kt:71` keeps its `skippedNotifications` in `rememberSaveable` too); the copy's own KDoc says the persistent surface is the one-line recovery row, not this sentence (`domain/RestNotificationCopy.kt:19-22`), which the dock and the rest page do show (`WorkoutDock.kt:253-257`, `RestTimerScreen.kt:242-246`). Below API 33 the dialog never opens.

**UI-2.** `canFinish` (`VM:210-211`) = found ∧ sets non-empty ∧ `!entryLocked`; `entryLocked` (`:202`) is `save.pending || logging || mutating || loadState != FOUND` — editing is none of these once `editSet` has returned. `finishWorkout` (`:2133-2136`) checks only `canChangeEntry()` (`:1520-1523`), which also ignores editing. The dialog's body is `EndWorkoutCopy.body(loggedSets)` only. Nothing is lost from the database (the set keeps its stored values); what is lost is the typed correction and the intent. Counter-evidence: the dock derives `SAVE_CHANGES` before `FINISH` (`ui/workout/WorkoutPrimaryAction.kt:153,158`) — so the contract "Editing … take[s] precedence over ordinary completion" holds for the dock and not for the header. No test drives header Finish while editing (`finishIsDisabledWithZeroSetsAndWhileLogging`, `finishWaitsWhileASetIsStillBeingSaved` cover zero sets and saving).

**W2b-4 (from §1, pending packet).** The Log's coach call (`VM:561-575`) passes the live `draft`, `wantAnotherSet = core.wantAnother` (`:569`), `historySets = core.lastPerformance?.sets` (`:572`) and `editingSetId`. The rest page's call (`RestVM:139-155`, and the seed at `:75-90`) passes a draft rebuilt from `workoutDraftCache.get(sessionId)` (`:138`), `editingSetId = null` (`:149`), and takes the defaults `wantAnotherSet = false` and `historySets = emptyList()` (`ui/workout/SetMicroRecUi.kt:87-90`). So: (a) after **Add another set** the Log's `allowExtra` is true and its line names the extra set, while the page's inputs say the lift is done (`LIFT_DONE`) and its line is the done call or absent; (b) on a **lift's first set** the Log seeds the call from last session's working sets (`WorkoutMicroRecTest.theLastSessionsEffortSeedsTheFirstSet`: reason `FIRST_SET`, RPE 9), the page has no history and cannot — `RestTimerViewModelTest.kt:391-393` says so in its comment and tests only the hint-driven weight. Two smaller differences ride along: while a set is being edited the Log shows no call and the page does; and `WorkoutDraftCache.get` falls back to another lift's draft while the selected lift has none (`workout/WorkoutDraftCache.kt:52-56`), a millisecond window during prefill. Fix shape for the packet: give `RestVM` the same three inputs (`lastPerformance`, `wantAnotherSet`, `editingSetId`) — the first needs `WorkoutRepository.lastPerformance` read the way `VM:766` reads it.
