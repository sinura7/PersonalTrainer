## 2. Restore state machine (design before code, R01–R03)

The restore journal lives in `files/restore-journal/` as two files:
`incoming.json` (the decoded document to apply) and `state.json`
(`RestoreJournalRecord`). Room replacement is one SQLite transaction;
preferences (DataStore) and the bodyweight/block history tables are
written afterwards and are **not** atomic with it. Recovery bridges
those stores; it never pretends they commit together.

### 2.1 Phases

| Phase | Durable meaning | Room holds | Still owed | Workout start |
|---|---|---|---|---|
| (none) | No restore in flight. | consistent | nothing | allowed |
| `staged` | `incoming.json` + `state.json` written. Nothing touched. | old | everything | refused |
| `wiping` | Marked immediately before the Room transaction. | old **or** incoming; the witness decides | prefs, history tables, reconcile, reminders, cleanup | refused |
| `room` | Room transaction committed. | incoming | prefs + history tables (required), reconcile (required, idempotent), reminders (best effort), cleanup | allowed |
| `prefs` | Preferences and history tables applied. | incoming | reconcile, reminders, cleanup | allowed |
| `done` (new) | All required work finished. | incoming | delete `incoming.json`, delete `state.json` | allowed |

`staged` and `wiping` are the only phases in which a start could land on
tables about to be replaced, so they are the only ones that refuse a
start (`BackupRepository.restoreBlocksStart()`). In `room`/`prefs`/`done`
the training data is final and a workout may begin; recovery's remaining
work touches DataStore, the history tables, and the catalog under the
maintenance lock, which every start also takes.

### 2.2 Commit witness (R01)

The old witness was five row counts plus the lowest session id. Two
documents with identical counts and ids but different weights, notes,
activities, or preferences produced the same string, and recovery in
`wiping` could therefore mistake the original database for the incoming
one and apply the incoming preferences over untouched history.

`RestoreWitness` replaces it. It is a versioned SHA-256 (`w1:` prefix)
over a canonical JSON projection of exactly the tables `replaceRoom`
writes: exercises, exercise credits, routines, routine exercises,
finished sessions with their session exercises and set logs, schedule
slots, non-live activities and templates (nested blocks, sets, intervals,
muscles), schedule rules, occurrences, missed-work decisions, reminder
deliveries, and goals. Every list is sorted by a stable key at every
level, scalars are rendered as strings, nulls as JSON null, and the
projection carries no `exportedAt`, `version`, `app`, or preferences.
The same normalisation the mappers apply on write (null block fields
defaulting to `EXTERNAL`/`OTHER`/`false`/`0`) is applied on the document
side, so `witness(document) == witness(Room after replaceRoom(document))`
is a tested invariant. Unfinished sessions and live activities are
excluded on both sides — a backup never carries them and a workout
started after a crash must not make recovery undecidable.

The journal record stores `beforeWitness` (Room at stage time) and
`afterWitness` (the document). The legacy count fingerprints are kept so
a journal written by the previous build is still resolved on the old
rule.

### 2.3 Recovery decision table

| Journal phase | Decision |
|---|---|
| `staged` | Close the journal. Nothing changed. |
| `wiping` | `current = witness(Room)`. If `before == after` the content is the same either way: finish. Else if `current == after`: committed, finish. Else if `current == before`: rolled back, close the journal, nothing changed. Else (witness absent → legacy fingerprint rule; witness present but matching neither): **unresolved** — close the journal without applying preferences, record a durable recovery note naming the safety copy, never apply incoming preferences over an unproven database. |
| `room` | Apply preferences from `incoming.json`; on success mark `prefs`. If `incoming.json` is missing (only possible for a journal written by the old cleanup order or by external deletion): reconcile, close, record a note that settings could not be applied. |
| `prefs` | Reconcile the catalog, rebuild reminders (best effort), mark `done`, close. Does not need `incoming.json`. |
| `done` | Delete whatever cleanup left behind. Already finished. |
| unknown | Close the journal. |

Preferences failure after `room` (R02): the journal **stays** at `room`,
`incoming.json` is kept, the commit returns
`RestoreResult(preferencesRestored = false, settingsPending = true)`, and
Settings says the training data is in and settings will be finished on
the next launch or on **Finish restore**. Every later launch and every
Settings open retries; the retry is idempotent because
`setRestoredPreferences` writes every key unconditionally and replaces
the history tables wholesale. `CancellationException` is rethrown, never
converted into "settings could not be applied".

Cleanup interruption (R03): `done` is marked before the two deletes, so
a crash between them leaves a journal that recovery sweeps in one step.
Workout start is never blocked by `room`, `prefs`, or `done`.

### 2.4 Fault matrix

| # | Interruption point | Durable state | Recovery result |
|---|---|---|---|
| 1 | Before `stage()` | nothing | none |
| 2 | After `incoming.json`, before `state.json` | orphan incoming | swept on next `read()` |
| 3 | After `state.json` (`staged`) | staged | closed; nothing changed |
| 4 | After `mark(wiping)`, before the transaction | wiping, Room old | `current == before` → closed; nothing changed |
| 5 | Mid-transaction | SQLite rolls back | as 4 |
| 6 | Transaction committed, before `mark(room)` | wiping, Room incoming | `current == after` → prefs, reconcile, reminders, done, closed |
| 7 | After `mark(room)`, before preferences | room | prefs from incoming → continue |
| 8 | DataStore written, history tables not | room | prefs re-applied (idempotent) → continue |
| 9 | Preferences applied, before `mark(prefs)` | room | prefs re-applied → continue |
| 10 | After `mark(prefs)`, before reconcile | prefs | reconcile, reminders, done, closed |
| 11 | After reconcile, before `mark(done)` | prefs | reconcile again (idempotent) → continue |
| 12 | After `mark(done)`, before deleting incoming | done | both files deleted |
| 13 | After deleting incoming, before deleting state | done | state deleted (this was the permanent block in R03) |

### 2.5 Export/import size contract (R04)

Two budgets, both in `BackupScaleBudget`:

- `DOCUMENT_BYTES_MAX` = 8 MiB of **UTF-8** plaintext JSON (the signed
  P3.7/P8.5 ceiling; `ENCODED_BYTES_MAX` keeps that name as an alias).
- `RAW_FILE_BYTES_MAX` = 12 MiB read from a picked file or a Drive
  download (`IMPORT_BYTES_MAX` keeps that name for the bounded reads).
  A protected envelope of an 8 MiB document is at most
  base64(8 MiB + 16-byte tag) plus a fixed header, about 11.2 MB, so the
  largest document the app will export still round-trips.

Every export path — plaintext file, protected file, Drive upload,
protected safety-copy export — measures the bytes it is about to write
and refuses with `TOO_BIG_TO_EXPORT` **before** writing or reporting
success. Import checks the raw file against `RAW_FILE_BYTES_MAX` and the
decoded document against `DOCUMENT_BYTES_MAX`. Sizes are UTF-8 byte
counts, never `String.length`.

Memory cost of the raised raw ceiling: about 70 MB transient at the
worst case (12 MiB raw bytes, its String, the decoded ciphertext, the
plaintext bytes and String) versus about 48 MB before. Acceptable on the
supported range; recorded here so it is a decision, not an accident.
